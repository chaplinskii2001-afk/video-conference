# ИСПРАВЛЕНИЕ ОТОБРАЖЕНИЯ ПРОГРЕССА В ИНТЕРФЕЙСЕ

## 🔍 НАЙДЕННАЯ ПРОБЛЕМА

**Симптом:** Прогресс обработки начинает отображаться только с пункта диаризации (55%), пропуская все предыдущие этапы (0%, 5%, 10%, 12%, 20%, 50%).

**Корневые причины:**

### 1. Задержка в начале опроса прогресса (ОСНОВНАЯ ПРОБЛЕМА)
Фронтенд начинал опрашивать прогресс только **через 2 секунды** после запуска обработки. За это время быстрые этапы (подготовка аудио, загрузка моделей) уже завершались, и фронтенд видел только поздние этапы.

**Последовательность событий:**
1. Клиент отправляет запрос на обработку → `/batch/process` (t=0)
2. Сервер создает задачу и запускает фоновую обработку (t=0.1s)
3. Клиент получает batch_id и запускает setInterval (t=0.2s)
4. **ПЕРВЫЙ запрос прогресса происходит через 2 секунды (t=2.2s)** ❌
5. За это время обработка проходит через:
   - 0% - task_started (t=0.2s)
   - 5% - preparing_audio (t=0.3s) 
   - 10% - loading_ai_models (t=0.5s)
   - 12% - Whisper загружен (t=1.0s)
   - 20% - transcribing (t=1.5s)
   - 50% - transcription_completed (t=2.0s)
   - 55% - diarization_completed (t=2.1s) ✅ **← Первый увиденный статус**

### 2. Слишком большой интервал опроса
Интервал опроса в 2 секунды был слишком большим для быстрых этапов, что приводило к пропуску промежуточных обновлений.

### 3. Последовательные обновления без задержек
Некоторые обновления прогресса происходили мгновенно друг за другом (например, 50% → 55%), что не давало UI времени на отображение промежуточных состояний.

## 🛠 ВНЕСЕННЫЕ ИСПРАВЛЕНИЯ

### 1. Немедленный первый запрос прогресса (КРИТИЧЕСКОЕ)
**Файл:** `static/script.js`

Вынесли логику опроса в отдельную функцию `checkProgress()` и вызываем её **немедленно** перед запуском интервала:

```javascript
async function checkProgress() {
    if (!currentBatchId) {
        stopProgressTracking();
        return;
    }

    try {
        const response = await fetch(`/batch/progress/${encodeURIComponent(currentBatchId)}?client_id=${encodeURIComponent(clientId)}`, {
            headers: { 'X-Client-Id': clientId }
        });

        if (!response.ok) {
            if (response.status === 404) {
                stopProgressTracking();
                localStorage.removeItem(STORAGE_KEYS.activeBatchId);
                currentBatchId = null;
                hideProgress();
                document.getElementById('process-btn').disabled = false;
                showError('Задача не найдена (возможно, сервер был перезапущен)');
            }
            return;
        }

        const data = await response.json();
        handleBatchProgress(data);

    } catch (error) {
        console.error('Ошибка при проверке прогресса:', error);
    }
}

function startProgressTracking() {
    stopProgressTracking();

    // Делаем первый запрос немедленно, чтобы не пропустить начальные этапы
    checkProgress();

    // Затем запускаем периодический опрос каждые 500 мс для более отзывчивого UI
    progressCheckInterval = setInterval(checkProgress, 500);
}
```

**Результат:** Фронтенд видит начальный статус (0%, task_started) сразу же после запуска обработки.

**Файл:** `static/script.js`

Интервал опроса уменьшен с **2000 мс** до **500 мс**:

progressCheckInterval = setInterval(checkProgress, 500);

**Результат:** UI обновляется в 4 раза чаще, что позволяет отслеживать даже быстрые этапы.

## 🎯 ПРЕИМУЩЕСТВА РЕШЕНИЯ

1. **Немедленная обратная связь:** Пользователь видит начало обработки сразу
2. **Полная информация:** Все этапы отображаются, ничего не пропускается
3. **Плавный прогресс:** UI обновляется чаще (каждые 500 мс вместо 2 сек)
4. **Надежность:** Даже при очень быстрой обработке все этапы фиксируются
5. **Минимальный оверхед:** Задержки по 100 мс не влияют на общее время обработки

## 🔧 ТЕХНИЧЕСКОЕ ОБЪЯСНЕНИЕ

**Почему это работает:**

1. **Синхронизация:** Фронтенд подключается к мониторингу до того, как начинается реальная обработка (задержка 100 мс после первого обновления)
2. **Частый опрос:** Интервал 500 мс достаточно мал, чтобы поймать даже быстрые этапы
3. **Гарантированная видимость:** Задержки 100 мс между обновлениями гарантируют, что каждое обновление будет зафиксировано хотя бы одним опросом
4. **Атомарность:** Каждое обновление прогресса сохраняется в файл синхронно, что исключает гонки данных
